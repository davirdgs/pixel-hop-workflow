# Workflow: release-status

1. Follow `_common.md`; load the target release metadata, artifacts, research, evidence, metric snapshots, experiment ledger, source specs, and current candidate/store state when cheaply verifiable.
2. Derive readiness, planning completeness, launch-gate/hash validity, actual rollout/availability, observation health, budget/spend, data quality, active experiments, blockers, external boundaries, and the next legal action.
3. Distinguish `not_started`, genuinely ready, pending human approval, pending console/device/review work, `insufficient_data`, operational alert, and growth learning. Never turn an uploaded build into `launched` or a noisy metric into a trend.
4. This workflow is read-only.
